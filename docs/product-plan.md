# dot 체중 관리 홈페이지 기획안

작성일: 2026년 10월 8일

연결 대상은 Firebase 프로젝트 `health-6b756`이다. 2026년 10월 8일 사용자 안내 기준으로 Blaze 요금제 설정, Firestore 생성, Authentication 활성화, 웹 앱 생성이 완료되었다. 웹 SDK 설정 입력 양식은 저장소의 `.env.local`이며, 빈 예시는 `.env.example`에 둔다.

체중, 식단, 운동 기록을 한곳에 보관하고 ChatGPT의 dot가 이를 조회·기록·분석하는 개인용 홈페이지를 만든다. 사용자는 평소처럼 dot와 대화하거나 홈페이지에 직접 입력한다. 두 경로의 기록은 같은 데이터베이스에 저장된다.

dot는 신체정보를 기록하고 음식 사진·설명에 맞는 영양정보를 검색하거나 근거를 남겨 추정한다. 안정 시 대사량, 섭취량, 운동 및 하루 소비열량은 최신 기록으로 자동 계산한다. [신체정보와 열량 계산 상세 설계](energy-calculation.md)에 원본 구조, 계산 방법과 재계산 규칙을 정의한다.

핵심 목표는 **오래 사용해도 기록을 다시 설명할 필요가 없고, 어떤 데이터에 근거한 분석인지 확인할 수 있는 것**이다. 홈페이지는 원본 기록과 통계를 관리하고, dot는 필요한 범위의 데이터를 읽어 해석과 제안을 담당한다.

## 서비스 범위와 기본 가정

- 첫 버전은 본인 1인의 건강 데이터에만 접근할 수 있는 서비스로 설계한다. GitHub Pages의 화면 파일은 공개될 수 있으므로 데이터 접근은 Firebase 쪽에서 인증과 권한으로 제한한다.
- 호스팅은 GitHub Pages, 백엔드는 Firebase를 사용한다. 로그인은 Firebase Authentication, 기록 저장은 Cloud Firestore, 서버 처리는 Cloud Functions for Firebase를 사용하는 안이다.
- 한국어와 모바일 사용을 우선한다. PC에서는 기간별 기록과 분석을 넓게 볼 수 있다.
- 날짜 기준은 Asia/Seoul이다. 실제 측정·식사·운동한 날짜와 입력한 날짜를 구분한다.
- 실제 현재 체중, 목표 체중, 목표 기간은 초기 설정에서 사용자가 입력한다. 임의의 건강 목표를 기본값으로 넣지 않는다.
- 대화는 ChatGPT의 dot에서 진행한다. 초기 홈페이지에는 별도의 AI 채팅창을 만들지 않는다.
- 체중 변화 관찰과 생활 기록 관리에 집중한다. 특정 감량 속도나 식단 처방을 서비스가 자동으로 결정하지 않는다.

## 사용 방식

### dot에게 말해서 기록하기

사용자가 “오늘 아침 몸무게 78.4kg, 점심은 비빔밥 한 그릇, 저녁에 40분 걸었어”라고 말한다. 이 수치는 기능 설명용 가상 예시다.

1. dot가 현재 날짜와 시간대를 확인하고 체중, 식단, 운동 기록으로 나눈다.
2. 명확한 사실은 바로 저장 요청한다. 음식 영양정보와 운동 강도는 적합한 자료를 조회하고, 필요한 추정은 근거·가정을 붙인다. 근거 없이 값을 정할 수 없으면 미상으로 둔다.
3. 서버가 저장 결과와 각 기록의 ID를 반환한다.
4. dot가 저장된 날짜와 내용을 짧게 알려준다. 홈페이지에도 같은 기록이 나타난다.
5. 사용자가 “걷기는 어제였어”라고 정정하면 해당 기록만 수정한다.

저장에 실패한 항목은 성공한 항목과 구분해서 알린다. 중간에 연결이 끊어져 재시도해도 같은 기록이 중복 생성되지 않아야 한다.

### 홈페이지에서 직접 기록하기

홈 화면에서 체중·식단·운동 중 하나를 선택해 입력한다. 식단은 음식 이름만, 운동은 종목만 먼저 저장할 수 있다. 상세 수치를 필수로 요구해 기록을 포기하게 만들지 않는다. 최근 음식이나 운동을 다시 입력할 때는 복사 기능을 제공한다.

### 쌓인 기록으로 분석하기

사용자가 dot에게 “최근 한 달 체중과 운동을 같이 봐줘”라고 요청한다. dot는 목표와 최근 30일 통계를 먼저 조회하고, 해석에 필요한 날짜의 원본을 추가 조회한다. 결과는 관찰된 변화, 데이터가 부족한 부분, 검토할 행동으로 나누어 홈페이지의 분석 기록에 저장한다.

홈페이지의 분석 화면에는 결과와 근거 기록 링크를 함께 표시한다. 이후 원본을 고치면 해당 분석이 이전 기록을 기준으로 작성되었다는 표시를 붙인다.

## 화면 구성

모바일 하단 메뉴는 **오늘 · 기록 · 변화 · dot 분석** 네 개로 구성하고, 목표와 데이터 관리는 상단 설정에 둔다.

| 화면 | 주요 내용 | 대표 행동 |
| --- | --- | --- |
| 오늘 | 최근 체중과 측정일, 기록된 섭취량, 하루 예상 소비량과 구성, 오늘 식단·운동 | 체중·식단·운동 빠른 입력, 계산 근거 확인 |
| 기록 | 달력과 날짜별 타임라인, 종류별 필터, 검색 | 과거 날짜 입력, 상세 조회, 수정, 삭제 취소 |
| 변화 | 7일·30일·90일 체중 그래프, 섭취·소비 추정 추이, 주간 운동, 기록 완성도 | 기간 비교, 근거 날짜 열기 |
| dot 분석 | 저장된 분석, 분석 대상 기간, 제안과 실행 결과 | 근거 확인, 제안 채택·보류, 재분석 요청 문구 복사 |
| 설정 | 신체정보, 생활 활동 기준, 목표, 선호·제약, 시간대, dot 연결 상태 | 신체정보·목표 수정, 연결 해제, 내보내기 |

오늘 화면은 위에서부터 날짜, 빠른 입력 버튼, 체중 추이, 오늘의 식단과 운동, 최근 dot 분석 순서로 배치한다. 최신 측정이 어제라면 “오늘 체중”으로 표시하지 않는다.

밝은 배경과 읽기 쉬운 숫자, 큰 입력 버튼을 사용한다. 빈 화면에는 첫 기록을 남기는 방법을 제시한다. 미기록, 추정값, 저장 중, 저장 실패를 색상뿐 아니라 글자로도 구분한다. 그래프에는 같은 수치를 읽을 수 있는 표를 제공한다.

## 첫 버전에서 기록할 정보

| 종류 | 최소 입력 | 선택 입력 | 처리 원칙 |
| --- | --- | --- | --- |
| 신체정보 | 항목, 값, 적용 날짜 | 키 cm, 나이 기준일 또는 생년월일, 대사식 계수 선택, 체지방률, 허리둘레 등 | 필요한 계산 입력을 확보하되 모르는 신체 특성을 추측하지 않음 |
| 체중 | 날짜, 체중 kg | 측정 시각, 공복 여부, 메모 | 하루 여러 번 측정 가능, 추이용 대표값은 하루 하나 |
| 식단 | 날짜, 음식 설명 | 끼니, 시각, 음식별 양, 기준 영양정보, 추정 범위와 근거 | 검색·사진 해석·유사 음식 추정을 구분하고 영양정보 없이도 저장 가능 |
| 운동 | 날짜, 운동명 | 수행 시간, 거리, 속도·강도, MET 출처, 세트·횟수·중량 | 운동 중 총소비와 기준선 대비 추가 소비를 구분 |
| 컨디션 | 날짜, 메모 | 수면 시간, 피로·배고픔 정도 | 보조 기능으로 제공하고 필수 입력하지 않음 |
| 목표 | 목표 설명, 적용 시작일 | 목표 체중, 검토일, 활동 목표 | 변경 이력을 보존 |
| 선호와 제약 | 사용자 설명 | 음식 취향, 생활 패턴, 운동 제약 | 사용자가 제공하거나 확인한 내용만 유지 |

체중의 첫 측정값을 그날의 대표값으로 제안하되 사용자가 바꿀 수 있게 한다. 대표값 변경은 통계에 반영하고 원래 측정 기록은 남긴다. 근력운동의 세트별 구조화 입력은 후속 버전에서 추가한다.

식단 영양정보에는 사용자가 입력했는지, 포장 표시를 옮겼는지, dot가 추정했는지 출처를 붙인다. 추정의 전제인 음식 양과 기준도 함께 남긴다. 사용자가 추정치를 확인했더라도 추정이라는 출처는 유지한다.

## dot의 기억을 보완하는 데이터 구조

정보를 세 층으로 나눈다. **원본 기록은 보존하고 요약은 다시 만들 수 있게** 한다.

| 층 | 보관 내용 | dot가 읽는 시점 |
| --- | --- | --- |
| 장기 맥락 | 현재 목표, 목표 변경 이력, 확인된 선호·제약, 채택한 행동 | 분석을 시작할 때 |
| 기간 요약 | 최근 7일·30일·90일 통계, 기록 누락과 추정 비율, 최신 분석 | 질문과 관련된 기간을 우선 조회할 때 |
| 원본 기록 | 날짜별 체중·식단·운동·메모, 출처, 수정 이력 | 세부 근거가 필요할 때 |

dot는 매번 전체 기록을 전달받지 않는다. 먼저 작은 맥락 묶음을 조회하고, 질문에 맞는 기간·종류·검색어로 원본을 더 읽는다. 원본 조회는 페이지 단위로 제한하고 다음 페이지가 있는지 명시한다. 요약에는 대상 기간, 생성 시각, 데이터 버전을 포함한다.

대화 전체를 저장하는 기능은 첫 버전에 넣지 않는다. 기록에 필요한 사용자 발언 조각과 구조화된 값, 분석 결과만 저장한다. dot가 제안한 내용은 사용자가 채택하기 전까지 목표나 사용자 사실로 취급하지 않는다.

### 주요 저장 단위

| 저장 단위 | 용도 |
| --- | --- |
| profile 및 goals | 사용자의 설정, 확인된 맥락, 유효 기간별 목표 |
| body_profiles 및 activity_baselines | 시점별 신체정보, 일상 활동 기준과 소비량 계산 전제 |
| food_references 및 meal_items | 출처별 영양 기준값, 음식별 섭취량·추정 근거 |
| weight_entries | 측정값과 하루 대표값 선택 |
| meal_entries | 음식·섭취량·영양정보와 정보 출처 |
| workout_entries | 운동 종목·시간·거리·상세 메모 |
| daily_checkins | 컨디션과 해당 날짜의 기록 완료 여부 |
| analysis_reports | dot 분석, 대상 기간, 근거 기록 ID, 데이터 버전 |
| action_items | 제안된 행동, 채택·보류·완료 상태, 사용자 피드백 |
| change_history | 누가 어떤 기록을 언제 수정·삭제·복원했는지 |

원본에는 고유 ID, 소유자, 발생 날짜, 알려진 경우 발생 시각, 입력 시각, 수정 시각, 입력 경로, 버전을 공통으로 둔다. 시각을 모르는 기록에 임의의 식사·운동 시각을 만들어 넣지 않는다.

Firestore에서는 사용자 문서 `users/{uid}` 아래에 종류별 하위 컬렉션을 둔다. 예를 들어 체중은 `users/{uid}/weight_entries/{entryId}`, 분석은 `users/{uid}/analysis_reports/{reportId}`에 저장한다. 하나의 문서에 모든 기록을 누적하지 않는다. 요청에 적힌 UID를 그대로 신뢰하지 않고 인증된 사용자로부터 조회 경로를 결정한다.

입력·수정 시 원본, 중복 방지 정보, 변경 이력, 사용자 데이터 버전을 Firestore 트랜잭션으로 함께 갱신하는 안이다. 날짜별 대표 체중의 선택 정보도 같은 처리에 포함한다. 조회는 날짜 범위와 페이지 크기를 제한하고 필요한 인덱스를 준비한다. 첫 버전의 키워드 검색은 선택한 기간 내 제한된 기록을 대상으로 하며 검색 범위와 다음 페이지 여부를 표시한다.

삭제는 우선 복원 가능한 상태로 처리하고 활성 통계에서 제외한다. 영구 삭제는 별도 동작으로 제공하며 원본·첨부·파생 요약의 삭제 범위와 백업 보존 정책을 안내한다.

## dot 연동 방식

기본 제안은 **Cloud Functions for Firebase에 MCP 도구를 구현하는 방식**이다. MCP는 dot가 홈페이지의 정해진 조회·저장 기능을 호출할 수 있게 하는 연결 규격이다. GitHub Pages에는 정적 화면 파일을 올리고, MCP 요청은 Firebase 쪽 HTTPS 엔드포인트로 보낸다.

dot는 연결된 플러그인을 통해 서비스의 정보와 도구를 사용할 수 있다. ChatGPT는 사용자 정의 MCP 서버의 읽기·쓰기 도구 연결을 지원한다. 실제 dot에서의 도구 노출과 호출 가능 여부, 계정 권한, 승인 동작은 초기 연동 시험으로 확인한다. [dot 연결 안내](https://learn.chatgpt.com/docs/dots/getting-started), [사용자 정의 MCP 서버 안내](https://developers.openai.com/api/docs/guides/custom-mcp-server)

홈페이지와 MCP는 같은 저장·조회·검증 로직을 사용한다. 브라우저에서 입력했을 때와 dot가 입력했을 때 결과가 달라지지 않도록 한다. DB 접속 권한을 dot에게 직접 넘기지 않는다.

웹은 Firebase Authentication으로 로그인한 뒤 ID 토큰을 서버 API에 전달한다. MCP는 별도의 OAuth 접근 토큰을 검증하고 같은 Firebase UID에 연결한다. 두 입구가 인증을 마친 뒤 공통 서버 로직에서 소유자와 작업 권한을 확인한다.

| propose_action | 사용자가 검토할 행동 제안 저장 |

일상적인 명확한 기록은 대화에서 저장을 요청하면 처리하도록 설계한다. 플랫폼이 요구하는 쓰기 승인은 따른다. 수정할 대상이 여러 개면 임의로 고르지 않고 확인한다. 첫 버전의 MCP에는 전체 삭제, 영구 삭제, 목표 자동 변경 도구를 제공하지 않는다.

쓰기 요청에는 중복 방지 키를 두고 재시도 시 기존 결과를 반환한다. 수정은 기존 버전이 일치할 때만 적용해 사용자의 최근 수정을 덮어쓰지 않는다. 도구는 성공 여부, 기록 ID, 저장된 값, 버전을 반환한다. dot는 서버 성공 응답이 확인된 항목만 저장 완료라고 답한다.

인증이 필요한 MCP 연결은 표준 OAuth 기반으로 설계하고, 웹 로그인과 동일한 소유자에 연결한다. 공개 주소를 안다는 이유만으로 건강 기록을 조회할 수 없어야 한다. [OpenAI의 MCP 인증 안내](https://developers.openai.com/plugins/build/auth)

Firebase Authentication을 추가하는 것만으로 ChatGPT의 MCP OAuth 연결이 완성되었다고 보지 않는다. Firebase 로그인과 연결되는 OAuth 인증 계층의 구현 또는 호환 제공자 연계를 초기 시험에서 확정한다. 인증 메타데이터, 사용자 동의, 토큰 발급·검증·만료·연결 해제를 확인한다. 웹 ID 토큰을 복사해 장기 MCP 인증정보로 사용하는 방식은 채택하지 않는다.

MCP 엔드포인트는 일반 HTTP 요청을 받는 함수로 구현하고 Streamable HTTP 호환성을 검증한다. 서버 인스턴스 메모리에 세션이 계속 남아 있다고 가정하지 않는 구조를 우선한다. Firebase 전용 callable 호출 형식을 dot가 직접 지원한다고 가정하지 않는다.

### 연결이 어려울 때

초기 시험에서 직접 연동이 불가능하면 인증된 홈페이지를 브라우저로 조작하는 경로를 검토한다. 이 경우에도 같은 서버 검증을 거치고 안정적인 버튼 이름과 입력 항목을 제공한다. 개발 중 브라우저 작업은 Browser 플러그인과 Chrome 확장 백엔드를 사용한다.

연동이 끊긴 동안에는 홈페이지 직접 입력과 기간 요약 내보내기를 사용할 수 있다. 내보낸 요약으로 dot에게 분석을 요청할 수 있지만, 수동 전달만 가능한 상태를 자동 연동 완료로 보지 않는다.

홈페이지에서 “분석 요청 문구 복사”는 제공할 수 있다. 버튼 하나로 기존 dot를 즉시 실행시키는 기능은 별도 호출 경로가 검증되기 전에는 약속하지 않는다.

## 통계와 분석 기준

수치 계산은 서버가 담당하고 dot는 계산 결과와 원본을 해석한다. 같은 기간을 요청하면 홈페이지와 dot에 같은 수치가 보여야 한다.

신체정보·식사·운동·계산 전제가 바뀌면 관련 계산을 갱신한다. 조회 시에는 현재 데이터 버전에 맞는 결과를 반환한다. 계산 가능한 하루 합계를 dot의 기억에 계속 쌓거나 기준값으로 사용하지 않는다. 상세 식과 중복 방지 규칙은 [열량 계산 설계](energy-calculation.md)를 따른다.

| 지표 | 첫 버전 계산 방식 |
| --- | --- |
| 최근 체중 | 가장 최근 측정값과 측정 날짜 표시 |
| 7일 평균 체중 | 최근 7일 안에 기록된 날짜별 대표값의 평균, 측정일 수 함께 표시 |
| 기간 비교 | 같은 길이의 두 기간 평균과 각 기간의 측정일 수 비교 |
| 운동 | 실제 기록된 운동 시간 합계와 운동한 날짜 수 |
| 안정 시 대사량 | 유효한 신체정보를 이용한 공식 기반 추정, 공식·입력 날짜 표시 |
| 하루 예상 총소비 | 비운동 생활 기준선과 중복되지 않는 운동 추가 소비 반영 |
| 섭취·소비 차이 | 완성도와 추정 범위를 반영, 당일 부분 섭취와 하루 전체 소비를 확정 적자로 비교하지 않음 |
| 영양정보 | 알려진 값의 합계와 추정 포함 여부, 영양정보가 없는 식사 수 |
| 기록 현황 | 항목별 기록일 수, 사용자가 하루 기록 완료로 표시한 날 수 |

체중은 결측일을 보간하거나 0으로 채우지 않는다. 7일 중 3일만 측정했으면 “3일 측정 기준”이라고 표시한다. 운동 기록이 없으면 실제로 운동하지 않았다고 단정하지 않는다.

식단을 한 끼만 기록했다면 그날 전체 섭취량처럼 표현하지 않는다. 일별 영양 합계에는 “기록된 식사 기준”을 붙이고, 영양정보가 모두 비어 있으면 합계를 미상으로 표시한다. 기간별 하루 평균은 사용자가 하루 기록 완료로 표시하고 영양정보가 갖춰진 날짜를 기준으로 계산하며, 제외된 날짜 수를 보여준다. 추정값은 별도로 구분한다.

분석은 관찰된 사실과 가능한 설명을 구분한다. 함께 변한 지표만으로 원인을 확정하지 않고, 자료가 적으면 그 범위를 명시한다. 첫 버전에 대사량·소비량·섭취량의 자동 추정을 포함하되 이를 자동 식단 처방, 추가 섭취 허용량, 목표 체중 도달일의 단정적 예측으로 바꾸지 않는다.

분석을 저장할 때 조회 당시의 데이터 버전과 현재 버전을 확인한다. 분석 도중 기록이 바뀌었다면 다시 조회하거나 이전 데이터 기준임을 표시한다. 원본 수정·삭제·복원 시 관련 통계 캐시를 갱신하고 기존 분석에는 재검토 표시를 붙인다.

## GitHub Pages와 Firebase 구성

호스팅은 GitHub Pages, 백엔드는 Firebase로 정한다. 화면 구현은 React와 TypeScript를 Vite로 빌드하는 정적 웹 앱을 제안한다. GitHub Pages는 HTML·CSS·JavaScript를 제공하는 정적 호스팅이므로 인증 검증, 기록 저장, 통계 계산, MCP 실행은 Firebase 서버에서 처리한다. [GitHub Pages 공식 설명](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages), [Vite의 GitHub Pages 안내](https://vite.dev/guide/static-deploy.html#github-pages)

| 구성 | 담당 역할 |
| --- | --- |
| GitHub Pages | Vite로 빌드한 정적 화면 제공 |
| React와 TypeScript | 모바일 입력, 기록 탐색, 그래프, 분석 확인 |
| Firebase Authentication | 웹 로그인과 사용자 식별 |
| Cloud Firestore | 원본 기록, 사용자 설정, 목표, 분석, 변경 이력 보관 |
| Cloud Functions for Firebase | 웹 API, 인증·권한 확인, 입력 검증, 중복 방지, 통계 계산 |
| Cloud Functions의 MCP 연결부 | dot의 요청을 공통 서버 로직에 전달, OAuth 연결 검증 |
| Cloud Storage for Firebase | 후속 버전의 비공개 식사 사진과 첨부파일 |

데이터 요청 경로는 웹의 경우 `화면 → Firebase 서버 API → Firestore`, dot의 경우 `MCP → 공통 서버 로직 → Firestore`다. 첫 버전은 건강 기록의 읽기와 쓰기를 모두 서버 API로 통일한다. Firebase Authentication은 Google 로그인 등을 지원하며, 구체적인 로그인 제공자는 실제 연결 때 확정한다. [Firebase 웹 인증 안내](https://firebase.google.com/docs/auth/web/start)

### 정적 호스팅에 맞춘 화면과 연결

프로젝트 Pages 주소는 저장소 이름이 경로에 들어갈 수 있으므로 실제 주소에 맞춰 Vite의 `base`를 설정한다. 첫 버전의 화면 이동은 해시 라우팅을 사용해 기록 상세 링크를 직접 열거나 새로고침할 수 있게 한다. 서버 렌더링과 Next.js 서버 기능을 전제로 한 코드는 사용하지 않는다.

웹 API에는 실제 Pages 출처를 허용하는 CORS 정책을 적용한다. Firebase Authentication의 승인된 도메인과 선택한 로그인 방식의 동작도 확인한다. CORS는 브라우저 접근 정책이며, 데이터 권한은 별도로 서버에서 검증한다. 설정 변경은 배포 준비 단계에서 승인 후 수행한다. [Firebase HTTP 함수와 CORS](https://firebase.google.com/docs/functions/http-events)

정적 빌드에는 화면 코드와 공개 가능한 연결 설정만 포함한다. 건강 기록을 빌드 시 가져오거나 정적 JSON으로 내보내 공개 폴더에 넣지 않는다. 서비스 계정 JSON, 비공개 키, 토큰은 브라우저 코드나 빌드 산출물에 포함하지 않는다.

첫 버전에는 별도의 모델 호출 서버나 벡터 데이터베이스를 두지 않는다. 날짜·종류별 조회와 검색으로 시작하고, 자연어 검색의 실제 필요가 생기면 확장한다.

### 비용과 실행 환경

Cloud Functions의 로컬 에뮬레이션은 가능하지만 실제 배포에는 Blaze 요금제가 필요하다. 서버 함수, Firestore 읽기·쓰기와 저장, 백업, 추후 사진 저장 비용을 함께 검토하며 무료 운영을 보장하지 않는다. [Cloud Functions 시작 안내](https://firebase.google.com/docs/functions/get-started)

처음에는 Firebase Emulator Suite와 가상 데이터로 검증한다. 실제 프로젝트 연결, 결제 계정 연결, 리전·권한 설정, GitHub Pages 설정 및 배포는 별도 승인을 받은 후 진행한다. 배포 절차는 승인된 버전을 수동으로 실행하는 흐름을 기본으로 계획한다.

## 데이터 보호와 복구

- 로그인한 본인의 기록만 서버에서 허용한다. 웹 화면에서 숨기는 것만으로 접근을 제한하지 않는다.
- 서버 API를 통한 접근으로 통일하므로 Firestore 보안 규칙은 클라이언트의 직접 접근을 기본 차단하는 안이다. 서버 SDK는 Firestore 보안 규칙을 우회하므로 각 함수가 인증 토큰, 허용된 소유자 UID, 작업별 권한을 직접 검증해야 한다. 본인 이외의 계정이 로그인해도 건강 API를 사용할 수 없게 한다. [Firestore 보안 규칙의 적용 범위](https://firebase.google.com/docs/firestore/security/rules-conditions)
- 실제 건강 기록, 사진, 백업, 토큰은 Git에 넣지 않는다. 개발용 예시는 가상 데이터를 사용한다.
- 사진 기능을 추가할 때는 비공개 저장과 제한된 접근을 사용하고, 위치 메타데이터 처리를 함께 설계한다.
- 기록 내용을 일반 접속 로그나 오류 로그에 그대로 남기지 않는다. dot에는 요청에 필요한 범위만 전달한다.
- JSON 내보내기는 원본·출처·목표·분석을 포함하고, CSV는 체중·식단·운동별로 제공한다. 내보내기에는 형식 버전을 붙인다.
- 실제 사용 전 데이터베이스 백업과 별도 시험 환경에서의 복원 절차를 검증한다. 파일이 추가되면 첨부파일도 복구 대상에 포함한다.
- 연결 해제 이후 MCP 접근 차단을 확인한다. 삭제와 백업 보존 기간은 실제 운영 전 설정한다.

## 개발 순서와 완료 기준

### 1단계 dot 연동 검증

Firebase Emulator Suite와 가상 체중 기록 한 건으로 웹 인증, Firestore 저장, 공통 서버 로직을 먼저 검증한다. 이어서 Cloud Functions의 MCP 엔드포인트와 OAuth 계층을 시험해 사용자의 실제 dot에서 도구가 보이는지, 같은 사용자에게 연결되는지, 필요한 승인은 무엇인지, 저장 결과를 다시 읽을 수 있는지 확인한다. 계정 연결이나 외부 공개가 필요한 지점은 사용자의 승인을 받은 후 수행한다.

완료 기준은 **dot가 저장한 기록을 홈페이지가 읽고, 홈페이지에서 수정한 값을 dot가 다시 읽는 것**이다. MCP 경로가 막히면 원인을 확인하고 대체 경로를 결정한 뒤 본 구현을 진행한다.

### 2단계 일상 기록 기능

인증과 저장 구조를 갖추고 오늘 화면, 기록 화면, 목표 설정을 구현한다. 체중·식단·운동의 최소 입력, 과거 날짜 입력, 수정, 삭제 취소를 완성한다.

완료 기준은 휴대폰에서 최소 정보로 기록하고, 새로고침하거나 다른 인증된 기기에서 열어도 같은 기록을 확인할 수 있는 것이다.

### 3단계 변화와 분석

기간별 통계와 그래프, 신체정보 기반 대사량 계산, 음식 자료 검색·추정, 운동 및 하루 소비량 계산, dot 맥락 조회와 분석 저장을 구현한다. 계산 근거 링크, 원본 변경 시 재계산과 분석 재검토 표시를 포함한다.

완료 기준은 동일한 테스트 기록에 대해 홈페이지와 dot 조회 수치가 일치하고, 근거를 수정하면 통계와 분석 상태가 올바르게 바뀌는 것이다.

### 4단계 사용 전 검증

다음 시나리오를 통과한 뒤 실제 개인 기록으로 사용한다.

- 같은 저장 요청을 두 번 보내도 한 번만 기록된다.
- 웹과 dot가 동시에 수정하면 충돌을 감지하고 최근 내용을 무단으로 덮어쓰지 않는다.
- “어제” 기록과 자정 전후 입력이 한국 날짜 기준으로 정확히 저장된다.
- 체중 미측정일, 영양정보 없는 식사, 운동 미기록일이 0이나 완전한 하루 데이터로 오인되지 않는다.
- dot 연결이 실패해도 직접 입력은 가능하고, 저장 실패를 성공으로 표시하지 않는다.
- 권한 없는 요청으로 원본·분석·내보내기 자료를 읽을 수 없다.
- 다른 UID의 로그인, 만료·위조된 토큰, MCP 연결 해제 이후 요청을 서버에서 거절한다. Firestore 보안 규칙 검증과 서버 권한 검증을 각각 수행한다.
- 실제 Pages의 저장소 경로에서 화면 링크를 직접 열고 새로고침할 수 있으며, 로그인과 서버 API의 CORS 동작이 정상이다.
- 내보내기 내용이 원본과 일치하고 백업 복원으로 기록과 연결 관계가 유지된다.
- 음식의 분량·단위 환산, 대사량 공식, 운동 중복 방지, 당일 예상치 구분, 원본 변경에 따른 재계산이 [열량 계산 검증 기준](energy-calculation.md)의 가상 예시를 통과한다.

첫 버전의 성공은 화면 개수보다 **빠르게 기록할 수 있고, 기록이 유실되지 않으며, dot가 과거 정보를 정확하게 다시 읽을 수 있는지**로 판단한다. 실제 사용 중 자주 빠뜨리는 입력과 반복해서 요청하는 분석을 확인해 다음 기능의 우선순위를 정한다.

## 구현 전에 확정할 선택

본인 1인 사용, 모바일 우선, 한국어를 기본안으로 둔다. 첫 버전부터 dot의 음식 사진·설명 해석, 신체정보 기록, 섭취·소비열량의 자동 재계산을 지원하는 방향으로 설계한다.

GitHub Pages 호스팅과 Firebase 백엔드는 확정된 선택이다. Firebase는 사용자가 준비한 `health-6b756` 프로젝트를 사용한다.

| 준비 항목 | 상태 |
| --- | --- |
| Firebase 프로젝트 | `health-6b756` |
| 요금제 | Blaze 설정 완료 |
| Firestore | 생성 완료 |
| Authentication | 활성화 완료 |
| Firebase 웹 앱 등록 | 생성 완료 |
| Firebase 웹 SDK 연결 설정 | `.env.local` 입력 완료, 필수 항목·일반 형식·ID 일관성 확인, 실제 연결 검증 예정 |
| 실제 활성화한 로그인 제공자 | 확인 예정 |
| Firestore 데이터베이스 ID와 위치, 현재 보안 규칙 | 확인 예정 |
| GitHub 저장소와 Pages 주소 | 확인 예정 |
| MCP OAuth 연결과 실제 접근 검증 | 구현·검증 예정 |

클라우드 서비스의 준비 상태는 사용자 안내를 기준으로 기록했으며 아직 실제 프로젝트에 접속해 검증하지 않았다. 로컬 웹 SDK 설정은 값을 출력하지 않고 필수 항목, 일반적인 형식, 프로젝트 ID 및 앱 ID와 발신자 ID의 일관성을 확인했다. `.env.local`은 Git 추적 대상이 아니며 제외 규칙이 적용되어 있다. Authentication 활성화와 개별 로그인 제공자 설정은 구분해서 확인한다. 기존 데이터베이스의 위치는 먼저 조회하고, 새로 생성하거나 변경하는 것을 전제로 진행하지 않는다.

웹 앱 연결에 필요한 공개 설정과 실제 GitHub 저장소를 확인한 뒤 로컬 개발 구성을 준비한다. MCP OAuth 연결 방식과 예상 사용 비용은 구현·연동 검증 과정에서 확정한다. 이 문서는 최초 기획이며 현재 구현 계약과 검증 현황은 [구현 기록](implementation.md)을 따른다. 소스 구현 후에도 외부 배포, 자격증명 생성, 결제·권한 설정, 운영 데이터 변경을 수행하지 않았다. 실제 배포와 운영 설정 변경은 별도 승인이 필요한 실행 단계다.


## 구현 시 반영한 조정

공통 원본 컬렉션과 kind 구분을 사용하며, 웹과 서버가 동일한 계산 모듈을 공유한다. 웹은 인증된 스냅샷에서 계산하고 MCP는 서버에서 계산한다. 모바일은 네 개 메뉴와 상단 설정을 제공한다. 실제 클라우드/dot 연결은 배포 승인 후 검증한다. 자세한 API, 상한과 검증 내용은 [구현 기록](implementation.md), 실행 절차는 [배포 준비](deployment.md)를 따른다.
